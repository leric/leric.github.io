**上下文成本驱动的软件设计（Context-Cost-Driven Software Design）**，以获取正确修改所需充分上下文的成本来评价设计。它的核心标准是**上下文最小化原则（CMP）**：

> 对于一个系统现实中必须支持的那些修改，如果完成正确修改所需的充分上下文获取成本更低，这个设计就更好。

本系列提出的核心贡献，是**评价软件设计取舍的共同标准**。熟悉的设计原则可以放在这个标准下解释、比较，也可能在特定场景中被否定。说明模块化有助于理解，只是论证的起点；真正要回答的是，某个边界、抽象或架构在什么条件下值得采用。

## 五条相互衔接的主张

1. **面对现实的修改需求评价设计。** 软件在持续修改中演进。评价结构之前，先说明系统必须支持哪些修改。
2. **正确修改需要充分上下文。** 修改者必须掌握足以判断目标行为、约束是否保持、修改是否完整的事实。更便宜但不充分的上下文不满足这个标准。
3. **获取上下文有成本，设计可以改变它。** 上下文成本为原本诉诸不同原则的设计选择提供共同的比较依据。
4. **设计改变上下文的获取方式。** 减少、迁移、索引和检查描述了这种变换。类型、契约、测试或索引可能增加文本，却让必要知识更容易找到、理解或验证。
5. **更好的选择取决于修改模式。** 一种结构可能值得为反复发生的集成变更付出，却给小型、稳定的工具增加无用成本。脱离实际要支持的修改，没有普遍胜出的架构风格。

这是一条推导链：修改提出问题，正确性要求充分上下文，获取上下文产生成本，设计改变这些成本，而现实的修改模式决定这种改变是否划算。

## 评价标准、解释机制与设计选择

**上下文成本驱动的软件设计**是整体视角，**CMP** 是核心评价原则。**深度与广度**描述上下文成本如何增长，**上下文变换与上下文路由**解释设计如何改变获取过程。边界、局部性、测试、语言特性和架构风格，则是通过这些机制接受评价的具体设计选择。

传统设计知识提供了有价值的机制与例子。CMP 提出的贡献，是让它们的取舍可以放在共同的基础上讨论。遵循 SOLID、DRY 或 Clean Architecture 本身不足以证明一个设计合理：需要说明它降低了哪些必要上下文的获取成本，增加了什么代价，以及对哪些修改有效。

## 这个标准怎样改变设计判断

### 相似代码可能表达不同知识

两个表单的校验代码可能相似，但各自服务于独立变化的业务规则。抽出共享校验器可以减少重复，也可能迫使每次修改都要理解两套策略，以及区分它们的各种开关。在 CMP 下，如果规则独立变化，保留分开的实现可能更合理。如果两个表单表达的是同一个必须同步变化的不变量，让它拥有统一归属、让调用方可发现，反而能降低遗漏风险。判断依据是共享知识与修改闭包，不能只看文本是否相似。

### 接口需要承担真正的边界作用

增加接口看起来能改善关注点分离。但如果调用方仍须阅读实现、装配和错误处理细节才能改对，接口只是增加遍历，没有形成可信的停止点。直接调用可能成本更低。如果更强的契约让调用方能停下来，并支持现实中确实需要的变化，判断又会反转。要比较的是两种设计各自要求的充分上下文，而不是接口数量。

### 架构选择取决于修改形状

如果一个功能的界面、行为和持久化通常一起变化，垂直切片可以让修改更局部。如果业务策略相对稳定而外部集成经常变化，分离策略与适配器可能更有价值。两者都有适用条件；需要比较实际获取路径，包括验证和跨功能不变量。架构名称本身不能决定胜负。

## 常见误读

- **Token 优化：** Token 可以是观察智能体工作的一项数据，但不是设计目标。消耗更少，也可能只是遗漏了必要上下文。
- **上下文检索算法：** 检索处理已有材料；软件设计还决定改对究竟需要什么知识，以及当前材料能否可靠地表达这些知识。
- **传统原则的另一种说法：** 解释传统原则的好处只是论证的一部分。比较它们的成本、指出何时应该偏离某项原则，才是贡献不可缺少的部分。
- **代码量或信息量最小：** 比较受充分性与正确性约束。增加显式类型、测试和文档，可能让设计更好。

当前契约、配置与职责归属应当让当前行为可以理解。历史记录可以解释取舍，也可能提供必要的溯源信息；但如果每次都要重建旧 PR 的来龙去脉才能发现今天生效的规则，这种设计成本就值得检查。能明确表达的当前适用条件，应尽量进入持续维护的材料；真正必要的历史和领域复杂性仍须保留。

## 还需要验证什么

本系列提供设计论证与实例，尚未建立普遍校准的度量，也没有证明每次依据 CMP 的修改都能改善结果。比较设计需要可比的任务与正确性标准，并考虑修改者能力和工具的影响。文件数、Token 数和工具调用数都只是局部观测，不能单独证明上下文充分。

## 检查是否理解到位

读完后，可以尝试用具体例子和相应章节回答：

1. CMP 对评价软件设计贡献了什么？
2. 评价标准、解释机制与设计技术之间有什么区别？
3. CMP 在什么情况下支持偏离传统设计规则？什么条件会让判断反转？
4. 为什么代码更多、智能体阅读的 Token 更多，设计却可能更好？
5. 比较架构时，哪些对未来修改的假设决定了结论？

有用的回答应保持正确性与充分性要求，说清增加和避免的获取成本，并指出修改模式。只总结成“模块化让智能体节省 Token”，就遗漏了这里提出的核心贡献。这些问题是阅读检查，不代表已经完成独立理解效果评估。
